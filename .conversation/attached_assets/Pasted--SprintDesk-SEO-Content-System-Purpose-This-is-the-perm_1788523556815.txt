# SprintDesk SEO & Content System

## Purpose

This is the permanent SEO, search architecture, content strategy, and AI-search visibility authority for the SprintDesk marketing website.

SprintDesk is a task/project management SaaS that bridges personal productivity and team execution.

This skill works alongside:

- SPRINTDESK WEBSITE — MASTER PROMPT & BUILD GUIDE
- sprintdesk-frontend-experience

The Master Prompt controls execution order and page-specific implementation prompts.

The Frontend Skill controls visual design, UX, responsive behavior, accessibility, and motion.

This skill controls:

- Technical SEO
- Information architecture
- Search intent
- Metadata
- Canonicals
- Indexability
- Sitemap
- robots.txt
- Structured data
- Breadcrumbs
- Internal linking
- Blog architecture
- Topic clusters
- Article structure
- Product landing-page SEO
- AI-search visibility
- AEO / generative-search readiness
- Content integrity
- SEO QA

Do not override product truth, working functionality, or the established SprintDesk sitemap.

---

# 1. SOURCE-OF-TRUTH HIERARCHY

When instructions conflict, use this order:

1. Actual SprintDesk product capabilities and production implementation
2. Existing SprintDesk sitemap and information architecture
3. Master Prompt
4. Frontend/design system
5. This SEO & Content System
6. Implementation convenience

SEO must never invent product capabilities to satisfy a keyword.

Never create content simply because a keyword exists.

Never create pages simply because a feature exists.

Never distort the product architecture for SEO.

SEO should strengthen the existing information architecture, not flatten it.

1. Discoverability

# 11. AI-SEARCH / AEO PRINCIPLES

Optimize content so that search engines and AI systems can accurately understand and retrieve the information.

Do NOT treat AEO or GEO as a separate magic ranking system.

Foundational SEO remains important.

Focus on:

- Clear answers
- Strong topical relevance
- Explicit terminology
- Logical headings
- Self-contained explanations
- Evidence
- Accurate facts
- Consistent entity references
- Clear relationships between concepts
- Original information
- Fresh information when freshness matters

Write important claims so they can be understood without requiring the reader to infer missing context.

# 18. META DESCRIPTIONS

Every important indexable page should have a useful meta description.

A good description should:

- Summarize the page
- Reinforce the search intent
- Give the user a reason to click
- Be specific
- Avoid keyword stuffing
- Avoid generic boilerplate

Do not use the same description across multiple pages.

# 19. H1 / HEADING SYSTEM

Every indexable page should have one clear primary H1.

Use logical H2/H3 hierarchy.

Do not use heading tags merely for visual styling.

SEO controls semantic hierarchy.

These are separate concerns.

---

# 20. CANONICAL URLS

Every indexable page should have the correct canonical URL.

Canonical URLs should:

- Use the preferred HTTPS URL
- Use the production domain
- Avoid unnecessary query parameters
- Match the intended public URL
- Be self-referencing where appropriate
- Be consistent with sitemap URLs

Do not canonicalize substantially different pages to a single generic page merely to consolidate SEO.

Canonicalization is a signal, not a substitute for correct information architecture.

---

# 21. URL RULES

Use:

- lowercase URLs
- descriptive slugs
- hyphens
- stable paths
- meaningful hierarchy

Avoid:

- unnecessary IDs
- tracking parameters in canonical URLs
- meaningless slugs
- keyword-stuffed URLs
- duplicate URL variants

---

# 22. INDEXABILITY

Before allowing a page to be indexed, verify:

- It has a real purpose
- It has unique useful content
- It has a canonical
- It is internally reachable
- It is not accidental duplicate content
- It is not a staging/demo route
- It does not contain placeholder copy
- It is not an empty category/archive page

Noindex should be used intentionally, not as a cleanup substitute for bad architecture.

---

# 23. SITEMAP

The XML sitemap should contain canonical, indexable, meaningful URLs.

Include:

- Homepage
- Features
- How It Works
- Solution pages
- Pricing where appropriate
- Resource hubs
- Published indexable articles
- Published guides
- Published templates

Do not include:

- noindex pages
- redirect URLs
- duplicate URLs
- tracking URLs
- private application routes
- authenticated dashboard routes
- staging routes

Use accurate lastmod values when the content meaningfully changes.

Do not rely on artificial lastmod changes.

---

# 24. ROBOTS.TXT

robots.txt should:

- Allow crawling of public marketing content
- Reference the XML sitemap
- Avoid blocking assets required for rendering/indexing
- Avoid exposing private application areas to crawlers unnecessarily

Do not use robots.txt as a substitute for noindex.

Do not block a URL in robots.txt if search engines need to see its noindex directive.

Keep private product/application routes appropriately protected by the application itself.

# 33. PRODUCT CLAIMS

Before publishing a product claim:

1. Verify the feature exists.
2. Verify the described behavior.
3. Verify the relevant plan if pricing/availability differs.
4. Verify terminology against the actual product.
5. Verify screenshots represent the current product.
6. Verify links point to the correct page.

SEO must never become a reason to exaggerate the product.

---

# 34. COMPETITOR CONTENT

Competitor comparison pages should only be created when there is:

- genuine user intent
- meaningful differentiation
- sufficient factual evidence
- unique value

Do not create hundreds of "[Competitor] alternative" pages with only the competitor name changed.

Avoid thin programmatic SEO.

If comparison content exists, it must clearly explain:

- use case
- differences
- tradeoffs
- relevant SprintDesk capabilities
- who each option may suit

Do not make unsupported superiority claims.

---

# 35. PROGRAMMATIC SEO

Do not generate large numbers of pages from templates simply to capture keyword variants.

Programmatic pages are acceptable only when:

- each page represents a real entity/use case
- the data is accurate
- the pages are meaningfully different
- the pages provide user value
- the architecture remains understandable
- there is sufficient content quality

Quality and intent always beat page volume.

---

# 36. IMAGE SEO

For meaningful images:

- Use descriptive filenames
- Use appropriate alt text
- Keep alt text concise
- Describe what matters
- Avoid keyword stuffing
- Use width/height or aspect-ratio constraints to prevent layout shifts
- Prefer modern optimized formats where supported
- Lazy-load below-the-fold images when appropriate
- Prioritize important above-the-fold assets

Decorative images should use empty alt attributes where appropriate.

Do not describe decorative imagery as if it were important content.

---

# 37. PRODUCT SCREENSHOTS

Product screenshots are important explanatory assets.

When used:

- Show real SprintDesk UI where possible
- Use accurate states
- Keep text readable
- Avoid misleading fake data
- Add useful contextual explanation
- Ensure mobile layouts remain usable
- Avoid giant screenshots that create unnecessary layout shifts

Do not use fake dashboards as SEO illustrations.

# 47. KEYWORD CANNIBALIZATION

If multiple pages target substantially the same intent:

1. Determine whether both pages deserve to exist.
2. Differentiate their intent if possible.
3. Consolidate if necessary.
4. Redirect the weaker page where appropriate.
5. Update internal links.
6. Update canonical and sitemap signals.

Do not solve cannibalization by randomly changing keywords.

---

# 48. CONTENT CANNIBALIZATION RULE

- Does an existing SprintDesk page already answer this?
- Is this genuinely a different search intent?
- Can the existing page be expanded?
- Would a new page split authority?
- Where would this page fit in the topic cluster?
- What internal links would connect it?

If there is no clear answer, do not create the page yet.

# 62. PRE-PUBLISH CONTENT GATE

Before publishing any article, guide, template, or landing page, ask:

1. Who is this for?
2. What question/problem does it answer?
3. What is the search intent?
4. Why should this page exist?
5. What does it add that existing SprintDesk content does not?
6. What topic cluster does it belong to?
7. Which existing pages should link to it?
8. Which pages should it link to?
9. What SprintDesk capability is genuinely relevant?
10. Is every product claim verified?
11. Is the content useful without the CTA?
12. Is the page structurally understandable to search engines and AI systems?
13. Is the canonical correct?
14. Is the schema accurate?
15. Should this page actually be indexed?

If the answer to #4 or #5 is weak, do not publish the page.

# 63. SEO ANTI-SLOP RULES

Never create:

- 100 near-identical SEO pages
- keyword-stuffed headings
- keyword-stuffed footers
- generic AI introductions
- fake statistics
- fake testimonials
- fake reviews
- fake comparisons
- fake integrations
- fake case studies
- FAQ sections on every page
- identical metadata across pages
- duplicate feature landing pages
- meaningless category pages
- "best X" pages without genuine editorial value
- competitor pages with only names swapped

SEO should make the website more useful, not more bloated.

---

# 64. DESIGN + SEO COLLABORATION

The Frontend Skill controls visual expression.

This skill controls semantic/search structure.

Do not make visual headings enormous simply because they are H1/H2.

Do not remove semantic headings because they are visually inconvenient.

Use CSS to separate semantic hierarchy from visual scale where necessary.

Product UI should remain visually authentic.

SEO content must fit the established SprintDesk visual language rather than turning the website into an SEO template.

---

# 65. SEO + ANIMATION

Animation must never hide essential SEO content.

Important copy must exist in accessible HTML.

Do not require interaction to reveal critical information to crawlers or users.

Do not use animation as a replacement for content.

Scroll storytelling is appropriate for /how-it-works, but the underlying workflow content must remain structurally understandable.

---

# 66. SEO + ROUTING

Never create a route solely because a keyword tool suggests it.

Before creating a route:

1. Identify intent.
2. Check existing routes.
3. Check topic overlap.
4. Determine whether an existing page can satisfy the intent.
5. Determine internal-link role.
6. Determine canonical relationship.
7. Determine long-term maintenance value.

If a route has no durable purpose, do not create it.

# 68. CHANGE MANAGEMENT

When editing an existing page:

1. Inspect its current SEO implementation.
2. Identify what already works.
3. Preserve working metadata and structured data unless there is a reason to change it.
4. Check inbound internal links before changing URLs.
5. Check canonical implications.
6. Check sitemap implications.
7. Check redirects if the URL changes.
8. Check content overlap with other pages.
9. Make targeted changes.
10. Re-run SEO QA.

Do not rewrite the entire SEO system during an unrelated visual change.

# 69. FINAL SEO PRINCIPLE

SprintDesk should not try to "look optimized."

It should be:

- easy to crawl
- easy to understand
- easy to navigate
- useful for humans
- semantically coherent
- factually trustworthy
- internally connected
- technically sound
- genuinely helpful for the searcher's problem
- understandable as a product entity
- useful as a source for search and AI-generated answers

The goal is not more pages.

The goal is stronger pages.

The goal is not more keywords.

The goal is clearer intent.

The goal is not gaming AI search.

The goal is producing information that search engines and AI systems can confidently understand, retrieve, attribute, and connect to the right SprintDesk page.

When uncertain:

Choose clarity over cleverness.
Choose usefulness over volume.
Choose product truth over keyword opportunity.
Choose consolidation over duplication.
Choose evidence over claims.
Choose a better page over another page.
